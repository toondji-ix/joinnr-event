# ADR 0004: request lifecycle contracts

Date: 20 October 2026. Status: contract implementation; independent review and runtime enforcement open. Requirements: F-09–F-11, F-13, F-18 and NFR-08/09. Development owner: Codex under the user's authorization; product/research owner: the user. Privacy and independent reviewers remain unassigned.

## Context and scope

Phase four permits independent contract/threat work while discovery, provider, privacy and funding gates remain open. [ADR 0002](0002-contract-foundation.md) covered three operations. This adds four operations to [OpenAPI](../../packages/contracts/openapi.yaml): request creation, acceptance, decline and withdrawal. There are now seven operation contracts, generated TypeScript types and strict schema tests. No controllers, persistence, identity, matching, contact grants or provider integrations are installed.

The [PRD](../01-product.md), [API blueprint](../05-api.md), [data design](../04-data.md) and [UX review](../ux-design.md) agree that crossed requests must not auto-accept, only the receiver accepts/declines, only the sender withdraws, acceptance creates one connection, and contact disclosure requires separate bilateral grants. This package specifies those rules without ratifying open retention, pause, cancellation-feedback, age or style policies.

## Wire decisions and reconciliation

| Point                      | Contract precision and trade-off                                                                                                                                                                                                                                                                                                                                                                        |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Request creation           | `target_mid`, optional `recommendation_id` and `intro` only. No actor, event, status, role or contact assignment in the body. Omission of recommendation ID still requires the blueprint's received-request relation; arbitrary IDs never grant directory access.                                                                                                                                       |
| Duplicate/crossed creation | 201 for a new pending request; 200 for an existing pending request with its original sender/receiver unchanged. Both return the pending projection; neither creates a connection.                                                                                                                                                                                                                       |
| Request transitions        | No JSON body. Event/request identifiers are path parameters and actor identity comes from verified authentication. Reject unexpected bodies at the future API boundary, including privileged fields.                                                                                                                                                                                                    |
| Version semantics          | Require one strong quoted positive request version through If-Match; missing is 428, stale is 412, incompatible state is 409. Schema checks lexical shape; runtime must additionally check safe-integer range. Lists, wildcard and weak validators are unsupported.                                                                                                                                     |
| ETag after acceptance      | Acceptance consumes the request's version but returns the new connection's version. Decline/withdraw return the updated request version. Never use connection version as contact-grant version.                                                                                                                                                                                                         |
| Return projection          | Creation/decline/withdraw return a bounded public request projection; acceptance returns minimal active connection metadata. No grant availability, contacts, private goals, raw style or peer feedback. Separate response schemas express only these operation results, not the full lifecycle read model.                                                                                             |
| Input versus stored name   | The API's `intro` maps to the data design's `introduction`; responses use `introduction`. This is an explicit adapter mapping, not two stored fields.                                                                                                                                                                                                                                                   |
| Public labels              | Interest labels use a 160-character technical wire bound; public goal summaries retain their existing 160-character bound. Label strings are not taxonomy IDs and duplicate labels do not imply duplicate interest IDs. Ready avatar IDs are optional, with no storage URLs disclosed.                                                                                                                  |
| Retry ordering             | Creation and acceptance require idempotency keys. After authentication and live object/participant access checks, a matching committed acceptance replay can return safe current connection metadata without re-executing a pending-only transition. A different key encountering a terminal request gets a state/version failure. Never blindly replay a cached payload after block, leave or erasure. |
| Time and policy            | New sends and acceptance require live networking eligibility; terminal transitions cannot act on requests already expired at close. Scheduler delay never extends permission. Pair cooldown/rate limits must follow approved policy; this package selects no new duration or quota.                                                                                                                     |

Alternative: install placeholder handlers or database logic now. Rejected because they cannot demonstrate real authentication, transaction isolation or live authorization and would bypass the remaining gates. Alternative: a single generic mutation result with arbitrary status/contact fields. Rejected because it weakens operation-specific projection and disclosure checks. Stack and module ownership remain unchanged.

## Authorization, transactions and threat review

| Threat/scenario                             | Required enforcement                                                                                                            | Current evidence / later gate                                                                         |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Guessed request or cross-event membership   | Verify request/event and both composite membership relationships from current records; inaccessible resources yield generic 404 | UUID/schema checks only; real API/RLS tests in EX-04/11                                               |
| Sender accepts or third party mutates       | Bind authenticated actor to live receiver for accept/decline or sender for withdraw; staff roles give no participant override   | Operation metadata tests; actual role-denial tests still required                                     |
| Crossed sends and simultaneous acceptance   | Canonical pair lock plus unique pending pair/request connection constraints; no automatic acceptance                            | Pending-only 200/201 response tests; real PostgreSQL concurrency tests required                       |
| Accept versus block/leave/expiry            | Compatible lock order and one transaction for authorization, state transition, connection and outbox; deny invalidated access   | Required negative cases specified; no race test claimed                                               |
| Stale edit, duplicate retry or worker crash | If-Match before new transition, actor/route/body-bound idempotency, transactional outbox and consumer dedupe                    | Header/response shape checks; persistence and replay tests required                                   |
| Private data in nested projection           | Closed allowlists at envelope, request, both public profiles and connection; private fields absent from logs/outbox             | Strict rejection tests for contacts/style/private goals; runtime projection/redaction unimplemented   |
| Contact disclosure on acceptance            | Create no grant implicitly; contact read remains separately authorized and transactionally live                                 | Closed connection schema rejects grant/contact fields; bilateral-grant integration tests remain EX-12 |
| Oversized introduction/actor escalation     | Bounded nonblank text; reject privileged properties and unknown fields without stripping/coercion                               | Schema rejection tests; future runtime adapter must preserve semantics                                |

Safe telemetry is limited to correlation ID, action, status, latency and approved pseudonymous scope references. Introductions, profiles, contacts and request bodies must never enter telemetry. Future clients must preserve unsent drafts and recover from 412/409 without silently resending a transition. Additive generated types alone do not prove native consumer compatibility.

## Validation and handoff

Run `pnpm contracts:generate`, `pnpm contracts:check` and `pnpm check`. Contract checks compile schemas, validate synthetic examples and reject invalid inputs/private response fields. They do not prove SQL constraints, idempotency, authorization, native behavior or concurrency. No application route should be enabled on these checks alone.

Next independent work: review these contracts and expand remaining ungated contract surfaces. Persistence and provider spikes remain dependent on EX-02 reconciliation, G-01/G-03 and approved account/region inputs. D-06 confirms a test product with no assigned budget; no cloud spend or provisioning follows from this ADR. Full Phase 4 exit remains open.

Rollback is a source/type/test revision that removes the four added contracts; no database or deployment rollback exists because none changed. Preserve earlier ADRs as historical records.
